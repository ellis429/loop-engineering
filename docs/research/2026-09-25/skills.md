## Outer-loop collision — avoid invoking unchanged

The installed [subagent-driven-development](/Users/johnson.chiang/.claude/plugins/cache/claude-plugins-official/superpowers/6.3.0/skills/subagent-driven-development/SKILL.md) is already an orchestrator: fresh implementation workers, per-task review, fix dispatches, ledger recovery, final whole-branch review, and finish-branch handoff. Its local text permits autonomous rulings on ambiguities, five task fix rounds, parking residual findings with controller rulings, and exactly one final fix wave. It records plan-specific state in `.superpowers/sdd/<plan-basename>/` and deletes that workspace after clean final review. These semantics conflict with this user's unresolved-decision boundaries, reviewer/human-only closure, configurable cap, and durable evidence requirements. A successful local task can have parked findings, so it cannot imply PR Pass.

[executing-plans](/Users/johnson.chiang/.claude/plugins/cache/claude-plugins-official/superpowers/6.3.0/skills/executing-plans/SKILL.md) also owns plan execution, requires worktree setup, redirects to SDD when subagents are available, and requires finishing-a-development-branch at the end. It is not a neutral plan reader.

The [using-superpowers](/Users/johnson.chiang/.claude/plugins/cache/claude-plugins-official/superpowers/6.3.0/skills/using-superpowers/SKILL.md) bootstrap explicitly exempts dispatched subagents handling a specific task. It otherwise routes creative work into brainstorming and relevant process skills. The local [brainstorming](/Users/johnson.chiang/.claude/plugins/cache/claude-plugins-official/superpowers/6.3.0/skills/brainstorming/SKILL.md) has user approval before implementation, a separate architecture-path written-spec review, and additional interaction. It should not become a second discovery loop around the chosen grilling flow.

The user's explicit single-orchestrator instruction takes precedence over conflicting skill workflows. Record that adaptation in the integration design and generated plan header; do not silently keep an unconditional SDD/executing-plans directive that workers will later obey. Do not claim an unchanged full Superpowers integration when only task methods/rubrics are reused. The cached upstream contributor rules likewise prefer project-specific workflows as a separate plugin rather than changes to Superpowers core.

### Delivery loop wrappers

1. Discovery: directly use Matt `grilling` + `domain-modeling` + `codebase-design`. Persist decisions and confirmed test interfaces with design approval. No new discovery methodology and no automatic user-only entry point invocation.
2. Planning: a thin `delivery-plan` wrapper reuses Writing Plans content requirements, adds task DAG/scope/acceptance/tests/version IDs, and terminates by saving the plan for the single controller. Explicitly replace its outer execution handoff under the user's workflow instruction. Declare whether importing a pinned version or invoking the installed skill with a documented precedence override.
3. Implementation: a thin `delivery-implement` wrapper selects **one** TDD discipline (recommend Superpowers), consumes one authorized task, and saves result plus Red/Green/refactor/regression evidence. A runner captures commands, timestamps, exit codes, code/tree fingerprints, task lineage and log hashes; it should not ask an LLM to invent historical evidence. Red belongs to its earlier source snapshot; final validation belongs to integrated current PR head. Refactor may be recorded as considered/no change where appropriate, subject to approved policy.
4. Review: a thin `delivery-review` wrapper in a separate Codex runtime uses a pinned independent-review rubric and full spec/design/plan + entire PR base/head diff. Prefer one reviewer for MVP. If choosing Matt unchanged, budget its two subagents and preserve separate axes. If choosing the Superpowers rubric, do not dispatch further reviewers. Emit stable findings and versioned structured verdict, preserving unresolved IDs across rounds; never mutate reviewed branch.
5. Fix: a thin `delivery-fix` wrapper uses receiving-code-review, with one diagnosis method only when needed. It returns verified fixes or an explicit disputed/blocked result with reason and evidence; no closure authority. CI diagnosis is agent work; CI collection and gate verdict remain code.

All four new wrappers should share one schema/reference rather than duplicate methodology. Each needs a trigger, input envelope, allowed tools/scope, deterministic output path, completion vs gate distinction, and failed/blocked reporting. Existing sources need pinned file and reference hashes. The controller alone owns dispatch, persistence, retry counts, finding status transitions, GitHub outbox, reconciliation, gate evaluation, and Pass/Blocked. Issue/PR publication is explicitly authorized by this user's task, but only for the selected demo target.

Still to decide in grill: chosen TDD discipline/exemptions and evidence granularity; design approval and scope-change escalation; exact severity/blocking rules; review display and finding authority; retry/budget/parallel limits. Skills do not decide those policies.
