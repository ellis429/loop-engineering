## Major

**M1. G3 ignores all but one run when the same head has several runs.**
- **Where:** design.md §8 "Attempt 選擇"; validation.md §6 Checkout and h4; spec-delta.md §5 AC-G14.
- **Source:** AC-G14, AC-G13, D49.
- **Problem:** The candidate CI triggers on both `pull_request` and `push`. Every push therefore normally creates two runs of `loopctl-ci` for the same H. The ordering rule keeps only the highest `run_number` and ignores the latest attempt of every other run.
- **Failure scenario:**
  1. PR run #41 fails `unit-macos` on an intermittent race, and push run #42 succeeds. G3 passes and the real failure on H is hidden.
  2. Same effect: someone reruns #41 after #42, and the rerun fails or is pending. G3 still passes on #42.
- **Fix:** Either trigger the workflow on `pull_request` only, or require the latest attempt of every run for H of the selected workflow to be success (treat any disagreement as unknown). Add both cases to h4.

**M2. No Red rule for correction attempts or for tasks with several attempts.**
- **Where:** design.md §7 (Red is required only for each plan task) and §9 (Batch, 爭議); validation.md M-G1 and M-REV; tasks.md 3.1 and 8.1.
- **Source:** GAT-03 (Red traces to "同一 task／後續修正"), D26, AC-G06/G07, and A02/A13 in project intent.
- **Problem:** The candidate does not say:
  - whether a behavior-changing fix (including a `pre_review_g1` fix) needs its own original Red;
  - which attempt's Red counts when an earlier attempt was abandoned.
- **Failure scenario:** R3 is meant to demonstrate finding → fix → re-review. As written, a `correctness_security` fix passes G1 with Green at the new head and no failing test that proves the fix. Separately, when a task's first attempt is stopped and redone, the first attempt's commit is no longer an ancestor of H. g3b(c) then invalidates the Red, and there is no stated path other than an unexplained dead end.
- **Fix:** State explicitly that a behavior-changing fix attempt needs an original Red bound to its finding ID and batch, with the same three qualifications. Alternatively, record an explicit D11 policy that it doesn't. Also define that only attempts in H's lineage are eligible; if a task's only Red belongs to an abandoned attempt, the result is Blocked with that reason. Add a g-case and an r-case for each.

**M3. Rebasing onto a new base breaks every Red's lineage.**
- **Where:** design.md §4 (the `push --force-with-lease` retry example) and §8 (the base row: "需要整合…新的真實 head"); spec-delta.md §3 AC-G17.
- **Source:** AC-G06, AC-G17, D51-R02/R07.
- **Problem:** When integrating a new base is needed, nothing forbids a rebase or force-push.
- **Failure scenario:** The base moves and there is a conflict. The Implementer rebases, so every attempt commit is rewritten and none is an ancestor of H. g3b(c) invalidates every task's Red. The original Red can't be captured again, so G1 is permanently Blocked, or people are pushed to fake the evidence.
- **Fix:** Require new-base integration to be a merge on the feature branch with no history rewrite. Restrict push to fast-forward; the lease is only a guard. Add an h7/g3b case: rebased lineage → Red invalid → Blocked with a stated reason.

**M4. T2.3's tests depend on interfaces owned by T6.1, which comes later.**
- **Where:** tasks.md execution table (2.3 vs 6.1); validation.md w5 and w8; design.md §2 and §6.
- **Source:** AC-D04, AC-D06, D51 task ownership.
- **Problem:** w5 (native turn complete) and w8 (native-only result extraction) run in T2.3. They need to read native transcripts and worker state, which is `observe worker|native`. That interface is in `observe.py`, owned by T6.1, and T6.1 depends on 2.3. Separately, `decide resolve_read` is listed under 6.1, but `decide` lives in 2.2's `decisions.py`.
- **Failure scenario:** T2.3 can't meet its completion condition. If it builds the observation code itself, it touches paths outside its owned scope, and under the candidate's own qualification (a) its Reds become invalid.
- **Fix:** Either move `observe worker|native` and the `worker:`/`native:` read keys into T2.3's owned paths, or move w5 and w8 to T6.1. List `decisions.py` as a shared path for `resolve_read`.

**M5. The CI pass rule doesn't enforce the skip policy, so Linux-only tests may never run.**
- **Where:** design.md §11; validation.md §0 and §6 (`uv run pytest -q -ra`).
- **Source:** D51-R05, AC-G13, and the audit note on Linux-owned tests.
- **Problem:** The "unexplained skip = fail" rule applies only to local G1. G3 treats job success, meaning pytest exit 0, as enough, and pytest exits 0 when tests are skipped.
- **Failure scenario:** The fsync-ordering test legitimately skips on macOS during local G1. On `unit-linux` it also skips, for a non-platform reason such as a missing tool. The test runs nowhere, yet G1 and G3 both pass.
- **Fix:** Give each CI job the same rule, without adding a registry. For example, a conftest hook fails the session when a skip reason is not a platform condition. Add the case to h2.

**M6. `pr_ensure` can adopt the wrong PR (no base or marker check).**
- **Where:** design.md §4 "PR 正向路徑"; validation.md h10; spec-delta.md §1.
- **Source:** DUR-06 (a queryable marker is required), AC-D12/D13, AC-G01.
- **Problem:** "恰一個 → 沿用" and "查到相符的 PR → succeeded" never define what counts as a match. They don't check the expected base or an operation marker.
- **Failure scenario:** A PR opened earlier or by someone else on the same head branch, targeting a different base, gets adopted or accepted on readback. G2 then reviews that PR's base…head, head-only G3 passes, and Pass is issued for the wrong base.
- **Fix:** Record the expected base and a body marker for the `pr_ensure` operation. A match requires head, base, and marker (a pre-existing PR requires at least head and base); a mismatch is Blocked. Add both cases to h10.

## Minor

- **m1. Pass package is never defined or tested.**
  - Where: design.md §8 Pass; validation.md p1/p4 and §6.
  - Source: ORC-05, D49, spec-delta §5 ("Pass package SHALL 標示").
  - Problem: No test checks the Pass package's contents, including `github_rules_verified=false`.
  - Fix: Define the package and assert it in p1/p4.
- **m2. Partial continuation under AC-O23 is quietly deferred.**
  - Where: coverage.md O23 says the first slice stops everything and only the affected work stops in S2. spec-delta §8 and the deferred lists in design §1 and tasks don't mention this.
  - Fix: Declare the deferral in the spec delta and deferred lists, or mark the row as S1-W plus a partial S2 deferral.
- **m3. N/A is stricter than D26, and the change isn't declared.**
  - Where: design.md §7 N/A; validation g8.
  - Source: D26, GAT-04 ("依真實行為判斷").
  - Problem: Any diff that touches config or test code is automatically ineligible. For example, a comment-only change in a YAML file fails G1 and can't produce a Red.
  - Fix: Either judge eligibility by actual behavior (the Reviewer decides), or list this narrowing in spec-delta.
- **m4. No task step owns the formal OpenSpec sync.**
  - Where: README "開工前仍待定" requires it; tasks.md 0.1 has no step for it.
  - Problem: Assignments bind "spec digests". Unsynced formal specs, such as the formal AC-G15 mapping, would make the Reviewer flag head-only CI as a violation.
  - Fix: Add the sync step, with a done condition, to 0.1.
- **m5. Nothing defines when base integration is "needed".**
  - Where: design.md §8, base row.
  - Problem: Rerunning Green on an unchanged H is effectively a no-op.
  - Fix: Define the trigger, e.g. GitHub mergeable=false, a Reviewer finding, or a human decision.
- **m6. Each check can't be tied to its own tested SHA.**
  - Where: validation.md §6 ("上傳 `tested-sha` 產物").
  - Problem: With three required jobs, a single artifact per run can't bind each check-run to its tested SHA.
  - Fix: One uniquely named artifact per job.
- **m7. `resolve_operation` has no defined meaning or test.**
  - Where: design.md §2 lists `decide resolve_operation`; there is no d-case for it.
  - Problem: After an unknown `pr_ensure` or `push`, the human's recovery path could re-enable a blind create.
  - Fix: Define it as record-only: bind an observed identity, or mark confirmed not-delivered. Add a test.
- **m8. The policy file is unnamed and unowned.**
  - Where: design §8 and validation §6 say "`workflow.yaml` digest", but the workflow is `loopctl-ci.yml`.
  - Problem: It's unclear whether the digest is of the GitHub workflow file or a separate policy file, and no task owns the policy file.
  - Fix: Name the file and give it an owner.
- **m9. A G2 `blocked` verdict doesn't Block the feature.**
  - Where: design.md §8 G2; validation r1.
  - Source: AC-G03 (G2 unknown **and** the feature is Blocked).
  - Fix: Add the feature Blocked assertion.
- **m10. The status claims contradict each other.**
  - Where: README.md line 3 says independent review is complete. design.md's header says the R03/R05/R07 residuals were fixed in revision-11 and are still awaiting independent review, while the title still says revision-10.
  - Fix: Make the status and revision labels agree.
